# دليل التشغيل والمشاكل التي عولجت

هذا الملف يسجل المشاكل العملية التي ظهرت أثناء بناء DSACMS، سبب كل مشكلة،
الحل المطبق، وما يجب فعله عند تكرارها. أما ملفا PDF وDOCX في هذا المجلد فهما
وثيقتا المتطلبات الأصلية، وليسَا سجل تغييرات التنفيذ.

## 1. زر تحميل الصوت وPDF غير ظاهر

**السبب:** البطاقات وصفحة التفاصيل كانت تعرض التشغيل أو القارئ فقط دون ربط زر
تنزيل فعلي بالرابط المحفوظ.

**الحل:** أضيفت أزرار تنزيل مباشرة للصوت وPDF، وربطت بصفحة التفاصيل والبطاقات،
مع قارئ PDF مدمج للكتب.

## 2. المقالات والكتب غير موجودة في الواجهة

**السبب:** منطق العرض كان موجهًا للمحتوى الصوتي والبيانات التجريبية.

**الحل:** أضيفت أنواع `audio` و`article` و`book`، وعرض نص المقال، وقارئ PDF،
وفلاتر البحث وإحصاءات مستقلة لكل نوع.

## 3. النبذة ظهرت في المكان الخطأ

**السبب:** معلومات الشيخ وضعت ضمن الصفحة الرئيسية.

**الحل:** إنشاء صفحة `pages/about.html` مستقلة باسم الشيخ محمد أحمد الهادي
الكرار، وتبقى الصفحة الرئيسية مخصصة للمكتبة.

## 4. البيانات ظهرت في متصفح الرفع فقط

**السبب:** الحفظ كان في `localStorage`، لذلك لم تكن الأجهزة أو المتصفحات الأخرى
ترى المادة.

**الحل:** ربط إنشاء المواد والتصنيفات والحذف وتغيير الحالة بـ PostgreSQL عبر
Backend. `localStorage` لم يعد مصدر الحقيقة للمواد.

## 5. فشل تسجيل الدخول رغم صحة كلمة المرور

**السبب:** اختلاف بين المستخدم المحلي والمستخدم المخزن مركزيًا، واعتماد الواجهة
على بيانات تجريبية أو اسم مستخدم فقط.

**الحل:** إضافة `POST /api/auth/login` لقبول اسم المستخدم أو البريد واستخدام
تجزئة كلمات المرور في Backend. يجب ألا تُخزن كلمة المرور كنص صريح.

## 6. حساب مدير الموقع والصلاحيات

**الحل الحالي:** أدوار قاعدة البيانات هي `admin` و`manager` و`viewer`.
الـ `admin` يملك الإدارة الكاملة. أي اسم واجهة مثل `site_admin` يجب توحيده مع
الدور المركزي قبل الاعتماد عليه، لا تركه كقيمة محلية غير موجودة في قيد قاعدة
البيانات.

**تنبيه:** تغيير الأدوار واستعادة كلمات المرور يجب أن ينفذه Backend مع تحقق
من الصلاحيات، وليس تعديل `localStorage`.

## 7. جداول الهاتف كانت أعرض من الشاشة

**السبب:** الجداول صممت لسطح المكتب وبقيت بعرض ثابت.

**الحل:** عند عرض الهاتف تتحول الصفوف إلى بطاقات باستخدام `data-label`، وتم تقسيم
النماذج الطويلة إلى خطوات متتابعة بدل عرض كل الحقول دفعة واحدة.

## 8. رفع الملف توقف عند «جار حفظ البيانات»

**السبب:** نجاح رفع الملف لم يكن يساوي نجاح حفظ المادة، وكانت أخطاء API تعرض
رسالة عامة.

**الحل:** إضافة شريط تقدم، وتحسين رسائل `fetch` وXHR، وفصل مرحلة رفع الملف عن
مرحلة حفظ metadata، مع إظهار تفاصيل استجابة الخادم في سجل المتصفح.

## 9. خطأ `InvalidAccessKeyId` من Internet Archive

**السبب:** مفاتيح Internet Archive صالحة، لكن توقيع AWS Signature V4 عبر AWS SDK
لم يكن متوافقًا بشكل موثوق مع واجهة IA S3-like.

**الحل:** استخدام صيغة Internet Archive الموثقة:

```http
Authorization: LOW ACCESS_KEY:SECRET_KEY
```

لا تعيد استخدام المفاتيح التي ظهرت في محادثات أو سجلات اختبار؛ يجب تدويرها من
Internet Archive.

## 10. الملفات الكبيرة تفشل عبر Vercel

**السبب:** Vercel Serverless ليس قناة تخزين ملفات كبيرة؛ توجد حدود للطلب ووقت
التنفيذ والذاكرة.

**الحل المؤقت:** إبقاء proxy للملفات الصغيرة مع رسالة خطأ واضحة وحد حجم مؤقت.

**الحل الإنتاجي:** رفع مباشر من المتصفح إلى Cloudflare R2، ثم معالجة غير متزامنة
بواسطة Queue وWorker. هذا المسار موجود كـ scaffold في
`backend/workers/archive-worker`.

## 11. حذف المادة ثم عودتها بعد إعادة التحميل

**السبب:** الحذف كان محليًا في الواجهة ولم ينفذ `DELETE` مركزيًا.

**الحل:** ربط زر الحذف بـ `DELETE /api/materials/:id` وربط تغيير الحالة بـ
`PATCH /api/materials/:id/status`.

## 12. تعذر الاتصال بقاعدة البيانات

**أسباب تم اكتشافها:**

- عنوان API يشير إلى `localhost` بعد النشر.
- CORS لا يسمح بأصل Frontend.
- صيغة اتصال PostgreSQL تحتوي معاملات غير مناسبة لمكتبة `pg`.
- أخطاء Vercel ظهرت للواجهة كفشل اتصال عام.

**قائمة الفحص:**

1. افتح `GET /api/status`.
2. تأكد أن عنوان الواجهة هو Backend المنشور.
3. أضف أصل الواجهة إلى `FRONTEND_ORIGIN`.
4. راجع Vercel Function Logs.
5. استخدم رابط PostgreSQL صالحًا مع إعداد SSL المناسب.

## 13. تصميم الرفع الإنتاجي

التدفق المستهدف:

```text
Browser -> R2 (direct upload)
       -> Vercel API (metadata/control plane)
       -> Cloudflare Queue
       -> Archive Worker
       -> Internet Archive
```

Worker يستخدم إعادة محاولة مع backoff وjitter عند `429` و`5xx`، ويستخدم Dead
Letter Queue بعد تجاوز عدد المحاولات. لا تضع مفاتيح IA أو R2 في JavaScript
المحمّل للمتصفح.

## 14. إعداد Worker

من مجلد Worker:

```bash
cd backend/workers/archive-worker
npx wrangler queues create dsacms-archive-queue
npx wrangler queues create dsacms-archive-dlq
npx wrangler secret put IA_BUCKET
npx wrangler secret put IA_ACCESS_KEY
npx wrangler secret put IA_SECRET_KEY
npx wrangler secret put API_ORIGIN
npx wrangler secret put INTERNAL_CALLBACK_TOKEN
npx wrangler secret put PRODUCER_TOKEN
npx wrangler deploy
```

يجب إنشاء bucket باسم `dsacms-media` أو تعديل
`wrangler.jsonc`، ثم اختبار Worker قبل تحويل الواجهة إليه.

## 15. فحوص ما قبل النشر

```bash
# Frontend
node --check assets/js/main.js
git diff --check

# Backend
cd backend
npm run check
node --check controllers/content.js
node --check utils/r2.js
node --check workers/archive-worker/src/index.js
```

## 16. حذف سؤال مجاب يفشل برسالة «غير قادر على حفظ التغييرات»

**السبب:** نِقطة `/questions/sheikh/:id/reject` في Backend كانت تعمل فقط على
الأسئلة المعلّقة (PENDING) بتحويلها إلى REJECTED، بينما زر «حذف نهائي» كان
يُرْسَل لنفس المسار فأعاد الخادم 404 لأن السؤال المجاب لا يمكن رفضه.

**الحل:**
- أُضيف في Backend نِقطة `DELETE /questions/sheikh/:id` محمية بصلاحيات
  `SHEIKH` تحذف السؤال نهائيًا مهما كانت حالته (مجاب أو معلّق).
- في الواجهة: زر «حذف نهائي» للأسئلة المجابة يستدعي `DELETE`، بينما زر
  «رفض / تجاهل» للأسئلة المعلّقة يبقى يستدعي `/reject` مع رسالة تأكيد واضحة
  لكل حالة.

## 17. صلاحيات الشيخ محدودة رغم وجوب امتلاكه صلاحيات كاملة

**السبب:** في `initDashboard` كانت الواجهة تحذف من دور `SHEIKH` كل اللوحات
والتبويبات ما عدا «نظرة عامة» و«الأسئلة والفتاوى»، فلم يعد يستطيع إدارة
المحتوى أو التصنيفات رغم أن مسارات المحتوى في Backend قابلة للتحرير من أي
دور مسجل.

**الحل:** أُزيل تقييد التبويبات، فأصبح الشيخ يرى كل أقسام لوحة التحكم
(المحتوى، إضافة/تعديل مادة، التصنيفات، الأسئلة) — مع بقاء إدارة المستخدمين
وسجل العمليات حصرية للمديرين (`admin`/`site_admin`) لتفادي كسر مبدأ أقل
امتياز.

## 18. حذف 521 سطرًا من main.js يكسر الواجهة بالكامل

**السبب:** أخطاء في التعديل أثناء نقل التغييرات جعلت commit يحذف 521 سطرًا
من `assets/js/main.js` من غير قصد، فاختفى كود تهيئة الصفحات (boot) وظهرت
الإحصائيات شرطات ولم تُحمل المواد من قاعدة البيانات.

**الحل:** رُدّ الملف إلى النسخة الكاملة من commit سابق وأُعيد تطبيق التغييرات
المقصودة فقط، ثم رُفعت نسخة الكاش `?v=...` في جميع الصفحات لكسر المتصفحات
المخزنة. التحقق: `git diff <النسخة الشغالة>` يجب أن يظهر التغييرات القصدية
فقط.

## 19. أسرار وبيانات الاختبار

- لا تحفظ كلمات المرور أو مفاتيح IA/R2 في Git.
- دوّر أي مفتاح ظهر في الرسائل أو سجلات الاختبار.
- احذف ملفات الاختبار من Internet Archive بعد التأكد من عدم الحاجة إليها.
- لا تعتبر بيانات الجلسة المحلية دليل صلاحية؛ التحقق الحقيقي يجب أن يكون
  مركزيًا.
- قبل الإنتاج، راجع CORS، حدود الرفع، سياسة حذف ملفات R2، وسياسة حذف أو إبقاء
  نسخ Internet Archive.
